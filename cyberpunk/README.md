# Building the Eddie mod

This folder turns the Eddie robot into the game mod:

1. **`build_glb.py`** assembles the robot from its description packages (base STL meshes
   and URDF kinematics, both Kinova Gen3 7-DoF arms with vision module, Robotiq 2F-85
   grippers, the way `urdf/eddie_robot.urdf.xacro` does it). It writes game-ready GLB
   files, the collision shapes and the arm poses to `out/`.
2. **`install_wolvenkit.py`** imports them into the WolvenKit project in `../wolvenkit`
   with the WolvenKit CLI. It packs `eddie_robot.archive`, installs it and the CET mod
   into the game, and can write the release zip.

Players don't need any of this: see the [main README](../README.md).

## Prerequisites

- Windows with Cyberpunk 2077 (to install and test; packaging works without it)
- [git](https://git-scm.com/) and Python 3.12, e.g. via [uv](https://docs.astral.sh/uv/)
- [WolvenKit](https://github.com/WolvenKit/WolvenKit/releases) CLI 10.x
  (`WolvenKit.Console-*.zip`; tested with 10.0.0-beta.1)
- Cyber Engine Tweaks in the game

## Build

From this folder:

```bash
python fetch_deps.py                     # clones eddie_description, ros2_kortex, ros2_robotiq_gripper into ../deps (pinned)
uv venv -p 3.12 .venv
uv pip install -p .venv -r requirements.txt
.venv/Scripts/python build_glb.py        # writes out/ (about a minute: the arm poses are solved with IK)
.venv/Scripts/python install_wolvenkit.py --wolvenkit "C:/path/to/WolvenKit.CLI.exe" --game "D:/path/to/Cyberpunk 2077"
```

`install_wolvenkit.py` options:

- `--wolvenkit` / `--game`: or set `WOLVENKIT_CLI` and `CYBERPUNK_DIR`. Without them, it
  looks for `WolvenKit.CLI` on PATH and for the game in the usual Steam, GOG and Epic
  folders.
- `--no-install`: build `wolvenkit/packed` but don't touch the game.
- `--skip-import`: build the project as it is, without re-importing `out/`. Use it
  after changing only the mod's Lua; it needs neither the Python build nor `deps/`.
- `--package`: also write `../dist/eddie_robot-<version>.zip`, laid out like the game
  folder. The version comes from `wolvenkit/eddie_robot.cpmodproj`.

The CET mod lives in
`../wolvenkit/source/resources/bin/x64/plugins/cyber_engine_tweaks/mods/eddie_spawner`:
`init.lua` is written by hand, and `eddie_parts.lua` is generated by
`install_wolvenkit.py`.

## Tests

```bash
.venv/Scripts/python test_mod.py
```

This runs the CET mod against a mocked CET and game API. It checks spawning, follow, go
to, manual driving, walls, the castors and wheel spin, riding, the arm poses and
grippers against `build_glb.py`'s kinematics, holding and dropping weapons, firing, shooting what V hits,
and Guard mode with mock enemies. It runs once for each possible game yaw
convention. It needs `out/` and `eddie_parts.lua`, so run it after the build.

## Preview

`.venv/Scripts/python make_preview.py` writes `out/preview.html`, a three.js viewer.
It needs to be served over http, e.g.
`.venv/Scripts/python -m http.server 8765 --directory out`.

## Outputs (`out/`)

| File | What it is |
|---|---|
| `eddie_static.glb` | Everything baked into one object per material, named `submesh_XX_LOD_1` (WolvenKit's import naming). Large materials are split so no submesh exceeds 65k vertices. ~240k triangles (arms + grippers ~62k). With `MOVING_PARTS` (default) the drive units and wheels are left out of it. |
| `eddie_drive.glb`, `eddie_wheel_r.glb`, `eddie_wheel_l.glb` | With `MOVING_PARTS`: one KELO drive housing and its two wheels (hub + tyre), each in its own joint frame (pivot / axle at the origin, URDF axes: spin axis x). Used 4 times each; mirrored units are the same mesh turned 180° about the pivot. `eddie_physics.json` → `moving_parts` has the pivots, wheel offsets and wheel radius (52.8 mm). |
| `eddie_arm_*.glb`, `eddie_grip_*.glb` | With `MOVING_ARMS`: the 7 Gen3 links and the 9 Robotiq 2F-85 parts, each in its own link frame and shared by both arms. `eddie_static.glb` then keeps only the arm base links. `eddie_physics.json` → `moving_parts.arms` has the joint chain (parent, fixed origin, axis, joint variable; gripper mimic joints share one variable), the rest pose, and the poses for the mod. |
| `eddie_parts.glb` | Same geometry as a hierarchy following the URDF: `base_link` → drive units → wheels, and attachment → `base_link` → `shoulder_link` → … → `bracelet_link` → gripper for each arm. Each node sits on its joint frame, so rotating a node in Blender moves that joint. Use it to rig or pose the robot. |
| `eddie_collision.glb` | 26 convex hulls: chassis, torso, 4 drive units, 2 laser scanners, and per arm 8 link hulls + 1 gripper hull. Use these as the physics shape, not the visual mesh. |
| `eddie_physics.json` | Mass (113 kg), centre of mass, inertia tensor, bounds, joint pose used, submesh → material table, material → texture table, hull list. |
| `textures/` | Solid 64 px textures per material (`_d01` colour, `_r01` roughness, `_m01` metalness) for WolvenKit's `metal_base.remt`. |

Conventions: metres, glTF Y-up (Z-up after import), origin on the floor under the
robot centre, robot front along +Y after import. All meshes have smooth normals
(hard edges above 35°) and box-projected UVs at 0.5 m per tile, meant for the
game's tiling multilayered materials. The glTF materials carry the URDF / .dae
colours as plain PBR factors, as a reference for picking game materials.

## Tuning

At the top of `build_glb.py`:

- `ARM_POSE`: joint_1..7 per arm (default: `config/initial_positions_arm_*.yaml`); also
  the arms' rest pose in the game
- `ARM_TARGETS`, `WAVE_TARGET`, `WAVE_AMPLITUDE` / `WAVE_HZ`: the in-game arm poses as
  gripper targets (point, finger direction, opening direction; the right arm mirrors
  the left). They are solved with IK (about a minute) so that each pose, and the
  straight joint move to it from rest, clears the torso and chassis by 2 cm and leaves
  room for V riding on the torso. The build prints how close each pose gets and any
  overlap.
- `GRIPPER_CLOSURE`: 0 (open) to 0.8 (closed)
- `INCLUDE_ARMS`, `INCLUDE_GRIPPERS`
- `TRI_BUDGET` (base meshes), `DAE_TRI_RATIO` / `DAE_TRI_CAP` (arm and gripper meshes)
- `MIN_PART_MM`: loose STL parts smaller than this (mostly screws) are dropped
- `DECIMATE_AGGRESSIVENESS`, `SMOOTH_ANGLE_DEG`, `UV_METRES_PER_TILE`
- `KORTEX_PALETTE` / `ROBOTIQ_PALETTE`: which .dae colour becomes which material
  (the Gen3 base actuator is blue in Kinova's mesh; map `(0, 0, 255)` to
  `arm_grey` to drop it)

## How the mod works

`install_wolvenkit.py` imports the meshes and textures into the prop project and sets
up the materials. It adds a kinematic `entColliderComponent` to `eddie.ent`: one box
per hull, with the `Device solid visible` filter like the vanilla falling crate, and
113 kg. It also adds one mesh component per moving part. Then it builds the project
and copies `eddie_robot.archive` into `archive/pc/mod`, plus the CET mod
`eddie_spawner` (and the AMM `.lua`, if AMM is installed). Rerun it after every
`build_glb.py`.

`eddie_spawner` needs only Cyber Engine Tweaks: open the CET overlay, use the "Eddie" window to
spawn the robot 2 m in front of V or despawn it, and to drive the newest one:

- **Follow V**: keeps 2 m away and keeps facing V
- **Go where I look**: drives to the spot under the crosshair (up to 40 m)
- **Manual**: hold the keys bound to the six `eddie_*` inputs (forward, back,
  strafe left/right, turn left/right); the base is holonomic like the real KELO drives
- **Stop**, plus a speed slider (0.2–2 m/s)
- **Ride** / **Get off** (or the `eddie_ride` hotkey, within 10 m): V stands on top of
  the torso. W/A/S/D or the left stick drive relative to where V looks, Eddie turns to
  face V's view, and Jump gets off onto the floor next to it (right side first, then
  left, back, front). While riding, V's walking is switched off with the
  `GameplayRestriction.NoMovement` status effect and V is moved with Eddie every
  frame, which is how the FreeFly mod does it. Go where I look and Manual still work while
  riding; pressing W/A/S/D takes over again. Follow V is refused until you get off. If a
  save made while riding loads with V unable to walk, press the ride hotkey with no
  Eddie spawned to clear the lock.

- **Arms**:
  - **Poses:** Rest, Reach (both grippers forward at chest height), Arms up, and Wave
    (right arm raised, swinging a wrist joint).
  - **Grippers:** open / close.
  - **Hotkeys:** `eddie_arms_rest`, `eddie_arms_reach`, `eddie_arms_up`,
    `eddie_arms_wave`, `eddie_grip`.
  - **Movement:** the joints move together at up to 1 rad/s, so all of them arrive at the
    same time. This works while driving and riding.
  - **How it works:** each arm link and gripper part is an `eddie_part_<l|r>_*` mesh
    component, placed every frame from the joint values (forward kinematics over
    `eddie_parts.lua` → `arms`). Only the joint values change while the arms move.
  - **Collision:** the arm collision boxes stay where the arms are at rest.

- **Weapons**:
  - **Give: right / left hand** (hotkeys `eddie_weapon_right`, `eddie_weapon_left`):
    Eddie gets a copy of the weapon in V's right-hand slot (`AttachmentSlots.WeaponRight`):
    a new item of the same TweakDB record, spawned with the game's loot manager
    (`SpawnItemDrop`) as a world drop. V keeps her own weapon.
  - **Holding:** every frame the drop is teleported to the gripper's tool point (13 cm
    out from the gripper base), the barrel along the fingers. It's turned about that axis
    so it's upright in the Reach pose, which the arms go to if they were at rest. The
    gripper closes to 0.45 on it. It follows the arms in any pose, and while driving or riding.
  - **Finding the drop:** `SpawnItemDrop` only drops an item its owner has, so the copy is
    given to V first and goes straight back out. Its return value is false even when it
    works, so the drop is caught when it appears (`gameItemDropObject.OnGameAttached`,
    within 0.75 m of where it was asked for), with a targeting-system scan as a fallback.
    Only the drop is moved; the weapon object follows it.
  - **Letting go:** Drop weapons (`eddie_weapon_drop`), opening the grippers, or
    despawning. The game no longer simulates a drop that has been moved every frame, so
    the mod lets it fall itself: under gravity, turning onto its side, onto the floor
    below the gripper. If V picks it up from Eddie's hand, the gripper opens.
  - **Firing:** `AIWeapon.Fire` on the weapon object, with V as the owner (like the
    vanilla sniper nest), at the weapon's own trigger mode and rate
    (`AIWeapon.GetNextShotTimeStamp`). Fire once (`eddie_weapon_fire_test`) shoots along the barrel.
  - **Shoot what I shoot** (`eddie_combat`): `NPCPuppet.OnHit` from V (not from Eddie's own
    guns) picks the target. Eddie faces it, the gun swings onto its chest (within 75° of
    the heading) and fires within 20°, while a ray from the gun to the target is clear, until it's
    dead, defeated, out of range (40 m) or gone.
  - **Guard** (`eddie_guard`): every 0.5 s it looks for characters in
    `NPCPuppet.IsInCombatWithTarget(npc, V)` within 40 m, nearest first, preferring ones
    with a clear shot. It drives to 10 m from the target (2 m without a clear shot),
    never further than 20 m from V, and follows V when it's quiet.
  - **Tuning:** `WEAPON_OFFSET`, `HOLD_CLOSURE`, and the constants at the top of the combat
    and guard sections in `init.lua` (`COMBAT_RANGE`, `AIM_CONE`, `FIRE_CONE`, `CHEST`,
    `GUARD_DISTANCE`, `GUARD_LEASH`, …).

Hotkeys and inputs are bound in the CET overlay under Bindings → eddie_spawner.
Movement is kinematic (the entity is teleported every frame), with a floor probe
(follows ramps, won't climb steps over 4 cm or drive off drops) and a wall probe
in the driving direction.

The drive units swivel like shopping-cart castors: each one turns so its wheels
trail its pivot (10 mm castor offset), up to 8 rad/s, so reversing flips them
round. The wheels roll at ground speed (v / 52.8 mm), each from its own contact
velocity, so on a turn the inner and outer wheels spin at different rates. They
are 12 `eddie_part_*` mesh components in `eddie.ent` (rest pose baked in), moved
each frame with the game's `SetLocalTransform`; `eddie_parts.lua` (generated next
to `init.lua`) holds the layout. Set `MOVING_ARMS = False` in `build_glb.py` to bake
the arms back into the body, or `MOVING_PARTS = False` to go back to one rigid mesh.

For the manual route and the collision/physics options, see [INGAME.md](INGAME.md): WolvenKit project, mesh import via Blender,
materials, spawning with AMM, and the options for collision and physics.
Those steps happen in WolvenKit and the game on your machine and haven't been
tested from here.
